## 部分缓解与剩余边界

- 部署使用非 root 后端、仅私有 Docker 网络接入 PostgreSQL/Redis、本机文件目录 `0700` 和密文文件 `0600`。Compose 中固定网段和 80/443 端口仍要求安装前检查现有服务；新检查只覆盖 Docker 网段，不覆盖主机端口占用。
- Compose 当前让后端使用 `luma` 数据库所有者凭据，运行态数据库权限尚未拆成迁移角色与最小权限应用角色。已有安装的角色与 migration 依赖该所有权；需要先设计兼容迁移和回滚，不能在本轮直接换凭据。可选 S3 存储的实际 bucket policy 由部署者管理，本轮没有隔离对象存储验收。
- VPS 新格式备份使用 `age` 分别加密 PostgreSQL 转储和密文目录，认证清单绑定代码版本、UserID HMAC 标识及密文哈希；密钥保存在 `/opt/luma/config/backup-keys`，不进入备份。轮换后旧私钥保留。旧版明文目录仍能显式恢复或转换为独立加密副本，原目录不会被脚本删除。恢复前执行认证、归档和空间预检，破坏性阶段以加密原库快照与持久状态标记补偿；INT/TERM 自动尝试恢复。此机制尚未在 VPS/隔离 PostgreSQL 上完整验收；完全失陷的 VPS 可同时暴露本地恢复私钥与数据库运行态元数据。离线额外接收者密钥可改善跨机灾备，不消除该风险。
- 本次复核发现恢复预检把同一文件系统的数据目录与配置目录当作两份独立空间，可能在恢复中途耗尽磁盘；已合并计算占用。恢复日志现保留脚本副本，避免代码切到旧提交后失去 `recover` 入口。错误私钥、密文单字节篡改和危险 tar 路径的隔离验证均被拒绝；完整 PostgreSQL 恢复、断电与补偿仍未在隔离服务中验收，不能标记为已充分验证。
- iOS Keychain 使用 `WhenUnlockedThisDeviceOnly`；Face ID 是应用解锁门禁，并非所有 Keychain 条目的独立生物识别访问控制。丢失唯一设备且没有预备恢复材料时，私钥可能无法恢复。内存清除不作保证。
- 本机退出登录曾只清除本地会话标记，仍保留在线 Access/Refresh Token；现已同步删除当前账号的本机 Token，并在已有账号流程测试中加入断言。离线退出无法保证即时撤销服务器端已签发会话；设备丢失仍应从其他已登录设备执行撤销，服务器端效果需真实后端验证。
- Redis 限流使用原子脚本；故障时返回 503。实际抗滥用仍依赖代理正确覆盖转发 IP、网络层限速与独立环境验证。
- 服务器能够延迟、丢弃、排序事件，并可观察关系及时间元数据；客户端身份固定与事件认证不能证明恶意服务器不可阻断通信。旧版 v3 和历史编辑事件仍需独立兼容审查；不得静默降低 v4 验证要求。

## 后续治理：数据库权限与注销补偿

- 数据库最小权限仍需兼容迁移：`deploy/docker-compose.yml` 把 `POSTGRES_USER=luma` 的初始化账号及密码同时交给后端；PostgreSQL 镜像会使该初始化账号拥有管理员权限。`backend/cmd/luma/main.go` 又在 API 进程启动时执行 migration 和 UserID 索引补齐，不能仅替换连接串。安全拆分需要先将迁移移到独立的一次性任务，创建仅具所需表/序列 DML 权限的运行角色，并在新装、已有卷、备份恢复和旧版回滚中验证角色、默认权限与迁移顺序。当前没有隔离 PostgreSQL 恢复环境证明该路径，故未改生产部署凭据或执行 SQL；运行账号权限过大仍为未解决风险。

| P1：v3 编辑/Reaction 在目录查询、Token 刷新及上传返回后缺少统一的授权复核。 | `RemoteMessageRepository` 在私钥使用前、发送前与应用响应前校验解锁账号、当前固定指纹、好友/会话/消息归属和存续；`RemoteAPIClient.json` 复用既有 MainActor 发送前门禁。显式固定身份也要求当前账号解锁且好友仍存在。 | 扩展既有 v3 用例，合并覆盖编辑和 Reaction 在锁定/身份变化时不触达端点、正常请求可发送；身份替换回归覆盖锁定期间不能确认指纹。 |
| P1：队列上传的迟到成功可覆盖身份变化/撤销结果或已读状态；达到最大重试次数的初始消息会被过滤，后续无 initialHeader 的消息得以越过它。 | `OutgoingMessageQueue` 在等待后复核待发项/消息存续与调用方信任，停止越过失败队首；不把已读/送达回退为已发送，不在清理后写回失效模型，不静默删除可能仍有 crypto journal 的孤立请求。仓储正文/事件确认后再检查授权。 | 扩展同一离线队列回归：精确重试、失败队首、删除、身份变化、撤销和先到已读回执。 |
| P1：已保护 Refresh Token 回调，但新的设备登录仍能在本地退出后保存迟到 Token；旧请求的撤销响应可误清新凭据并触发其设备密钥清理。 | `RemoteSessionStore` 清 Token 时先更新非秘密 Keychain 认证代次；`RemoteAuthProvider` 在登录提交前复核代次及登记，注册响应复核代次/账号存续。`RemoteAPIClient` 只对仍匹配原请求凭据的撤销结果触发清理，过期响应按认证失效拒绝。 | 复用退出/刷新测试，加入未存 Token 时退出、迟到登录拒绝，以及旧请求撤销响应不删除新 Token；并发刷新和无 Token 离线撤销回归通过。 |

新增信任/认证代次记录不含私钥、Root/Chain/Message/Attachment Key，不进入 SwiftData 或便携备份。旧 Session、已有 Ratchet schema 和消息 wire 均不迁移或重派生；旧 Session 的指纹和版本是首次建立本机目录记录时的下限。账号/设备全量清理删除对应记录；显式好友/身份清理只在未完成 journal 已安全处理后移除该账号的目录记录。未知写入结果仍保留日志，不重置会话。认证代次在 `clearAll` 后保留为非秘密墓碑，防止尚未返回的认证任务复活凭据。

### 需要协议升级：跨设备可信目录（2026-10-23 补齐实施设计，尚未实施）

#### 已有保障和不能证明的内容

复核 `V4RemoteBundle.verified`、`V4PreKeyService`、`V4SessionVault.observePeerBundle` 和 `backend/internal/device/v4.go`：账号 P-256 公钥签名绑定设备 UUID、版本、v4 协商/签名公钥；设备签名绑定 Signed PreKey。本机 Keychain 下限拒绝已见设备换身份、版本倒退和同版本换 Signed PreKey；用户仍须带外核对并固定首次账号身份。服务端的活动设备列表没有账号签名的完整集合承诺，签名也未覆盖设备撤销。因此单条有效记录、HTTPS 和本机最高版本都不能证明目录完整或跨端一致。

| 恶意行为 | 目前可检测 | 仍缺少的证据 |
| --- | --- | --- |
| 替换已固定账号公钥、伪造账号/设备签名 | 本机固定指纹和签名校验拒绝 | 首次信任前的真实身份，仍需带外核验 |
| 返回本机见过的较低设备版本 | Keychain 下限拒绝 | 新客户端没有历史下限时的目录新鲜度 |
| 向 A/B 提供各自合法但互相矛盾的目录 | 不保证检测 | 独立见证的同一日志历史和跨端比较 |
| 隐藏新设备或撤销信息，返回非空合法子集 | 不保证检测 | 账号授权的完整集合及其最新状态证明 |
| 阻断、延迟，持续返回旧的合法完整目录 | 无法只靠签名排除 | 受见证的新检查点和有界新鲜度策略；超时只能停止发送 |
| 掌控合法设备/账号私钥或与全部见证串通 | 不在目录单独保证范围 | 撤销与密钥恢复、独立审计及可信带外渠道 |

#### 方案评估与选择门槛

- [Signal 透明目录实现](https://github.com/signalapp/key-transparency-server)提供可验证的查询/监控/历史日志；[独立 auditor](https://github.com/signalapp/key-transparency-auditor)持续检查更新并签检查点。适合作为成熟工程候选，不能据此认定 Luma 已集成、该版本已审计或拿来即用。两者的服务、部署和客户端验证依赖均须单独锁定提交、许可证及审计证据。
- [IETF Key Transparency Protocol](https://datatracker.ietf.org/doc/draft-ietf-keytrans-protocol/)目前仍是工作草案；候选实现可能有应用差异，不能把最新草案当稳定兼容标准。[RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html)是证书透明性，不提供现成的私密账号映射/最新值查找/完整设备目录方案。
- 不采用“服务器自签 JSON + 版本号”冒充透明性：恶意服务器能为两个分叉都签名。也不自行编写 Merkle/VRF/证明算法或移植不完整片段。选定有可复用客户端验证器、测试向量和独立评审的完整套件后，才能冻结 wire；本次没有添加依赖、API 或 SQL。

#### 应用层合同与接入点（实施提案，不是现有 API）

1. **账号授权快照**：引入版本化完整 roster：账号 UUID、已固定账号公钥及身份代次、单调 rosterRevision、上一快照摘要、所有设备 UUID/身份公钥/版本/签名预密钥摘要/撤销代次，以及签署者授权。账号身份签名授权整份 roster；设备变更不能仅靠服务器登录权限批准。签名序列化、域和套件沿用选定且经审阅的规范，必须先冻结向量再实现。设备集合排序/重复 ID、跨账号挪用必须有唯一编码规则。
2. **密钥与 PreKey 分离**：目录承诺绑定设备身份及签名预密钥版本；一次性 PreKey 领取仍走现有事务接口，不在公开日志逐个记录领取行为。领取结果中的设备及版本必须与同一被证明的 roster 对应，不能拿 roster A 的证明匹配 bundle B。分配 OTP 不证明 roster 新鲜度，也不能以 OTP 耗尽为理由静默遗漏已证明的目标设备。
3. **查询合同**：拟增 `POST /v1/key-directory/query`，带已授权目标账号、客户端已有日志检查点和账号 revision；返回完整签名 roster、选定套件的最新值查找/包含/历史一致性证明、日志签名检查点、独立见证签名及明确套件/日志 ID。无历史客户端仍须可信根引导；首次空证明不是成功。查找隐私采用该套件既有的私密索引/承诺方法，不将明文 UserID 放入公开可枚举日志，也不把普通 UserID 哈希视为匿名化。
4. **更新合同**：拟增 `POST /v1/key-directory/updates`，必须带账号授权快照及期望上一 revision/摘要，采用数据库 CAS；响应区分 pending-log 和 witnessed，不把接收请求当作已可信发布。服务端 outbox 保证设备变更与发布任务一致；见证之前不把新增设备交给要求透明性的发送者。撤销应立即阻止后端 Token/路由，但透明性未确认时客户端暂停该账号新发送，不能假装已完成目录更新。
5. **客户端验证顺序**：在 `V4PreKeyService` 外增加目录验证服务，先校验请求账号、账号签名和完整集合，再用成熟验证器验证承诺/查找/历史与检查点；核对独立见证和已固定信任根、单调下限以及新鲜度；最后确认 bundle 的设备身份和版本。通过后才允许 `V4MessageSessionService.prepare`，在 Token 等待后的发送门禁再核对相同目录授权代次。View/Repository 的业务入口和 v1/v2/v3/v4 历史读取不改。
6. **分叉与隐藏检测条件**：独立审计者须监控同一个部署的完整历史，并对共同检查点背书；至少一名满足所选套件策略的见证必须与日志运营方独立，信任根不可从同一未经验证的目录动态下载。客户端之间可以通过已认证通道比较检查点；是否选门限见证、多少签名及新鲜度窗口，须与套件威胁模型一并审查后固定。不同大小的检查点需验证一致性，不能直接判为攻击；相同版本不同根或不一致历史必须阻断。全部见证串通、客户端隔离及首次历史缺失仍有边界，不承诺实时/绝对检测。

没有账号私钥的历史设备不能由服务器代签；需通过已验证的授权设备重新批准，全部设备丢失则按明确身份重建/联系人重新核验流程处理，不能保留“已验证”假象。日志签名轮换需由旧可信根授权、独立见证并防回退；丢失客户端检查点后必须重新可信引导，不能从服务器任意新根开始并假装连续。

强制启用后，回滚 Backend 可保留增量表但不能关闭已有客户端的校验；历史消息可读，新发送遇到旧服务应停止。服务端 DB 恢复不能重写/回滚外部日志，必须与原日志检查点对账补发；若无法保持连续则安全停机，通过审阅的灾备程序恢复原日志。每步均需隔离服务故障注入、独立见证和双端测试，本轮仅完成设计。

### 本地与服务端边界复核

- 沿 `V4AttachmentCrypto`、`RemoteFileTransferService`、`FileTransferService`、`PrivateMetadataStore`、`SearchIndexService`、`BackupManager`、`KeychainManager`、后端 `device/v4`、`message`、`file`、`push` 和既有 SQL 核查：本轮未确认新的消息/附件明文、文件名或客户端私钥上传路径。附件密钥留在 Ratchet 密文及本机 Master Key 加密描述，附件缓存/待上传文件二次加密并使用 complete file protection；APNs 仍是禁用接口与通用通知文案。所查 Crypto/Security/Network/Storage/Repository 无 print/debugPrint/NSLog 明文输出调用；未抓取真实流量或检查生产运维日志。

- 服务器仍能观察账号、公开资料/公钥、设备与好友关系、路由、时间、大小、IP 和密文。本轮不实施元数据匿名化，不据此证明恶意服务端无法拒绝服务。

### 已实施但未充分验证

- 测试在 macOS 使用合成 `stat`/`findmnt`/`swapon` 响应检查权限策略分支，不证明 Ubuntu 的真实挂载、swap 或服务生命周期。未运行 Docker、PostgreSQL 恢复、真实更新失败回滚、主机断电、磁盘故障或 VPS；这些需要隔离服务验收。静态顺序断言不能替代数据库与文件一致性的故障注入。
