# 消息加密版本与 E2EE 演进

## 已实现的本地两个版本

| 版本 | 密钥来源 | 应用范围 | 安全含义 |
| --- | --- | --- | --- |
| v1 `localAESGCM` | 本机账号 Master Key | 正式本地聊天、备份恢复后的消息 | 保护本机指定消息字段；不能供另一设备直接解密。 |
| v2 `sessionAESGCM` | 本机模拟 Session 根密钥；新消息经对称链派生每条消息密钥 | 显式本机模拟入口 | 验证版本化加解密与会话架构；不代表真实远端 E2EE。 |

两版均用 CryptoKit AES-GCM，每次加密随机 nonce。消息 ID 和会话 ID 等信息作为认证数据绑定密文；v2 有消息序号时还绑定会话版本与序号。`Message.encryptionVersion` 缺省按 v1 读取，以兼容旧记录。旧 v2 无 `messageKeyIndex` 的记录仍按旧会话密钥路径解密。编辑消息需重新加密，不能复用旧的 nonce 或消息密钥。

## 当前不能宣称的能力

v2 的对端公钥来自本机模拟，缺少远端身份认证和可信公钥分发。一次性 PreKey 未纳入握手；会话根密钥保留以读取旧消息，对称链可从根重算，因此**不具备前向保密**。没有完整 Double Ratchet。v3 设备信封通过隔离后端和模拟器双账号功能验证，但尚未完成双实体设备验证与独立安全审计。UI 不得写“已完成 E2EE”。

## 未来协议门槛（设计中）

真实 E2EE 需要经认证的设备身份与透明密钥目录、预密钥握手的正式协议规范、每设备会话与重放保护、密钥轮换及销毁、乱序/离线处理、附件独立随机密钥和恶意服务器场景评审。服务端只持有公钥、密文和必要路由元数据；任何网络版本切换必须明确老 v1 本地数据怎样保留/迁移，并经独立安全审查。见[会话协议](Session_Protocol.md)和[威胁模型](../Security/Threat_Model.md)。

## v3 设备信封现状（已实现代码，未完成安全审计）

客户端现在可从后端领取好友和自身其他设备的公钥束，验证身份公钥对 Signed PreKey 的签名，并要求好友身份指纹先由用户通过可信渠道核对固定。每个目标设备使用独立临时 ECDH/HKDF 消息密钥与 AES-GCM 信封；接收端验证身份签名后将正文重新加密为本地 v1。与本机 v2 Session/Ratchet 分开，不迁移或删除旧消息。

该协议是设备间加密消息传输基础，**不是完整 Signal E2EE**：没有完整 Double Ratchet、透明公钥目录、可靠密钥恢复或独立安全审计。持久待发队列与已登记设备撤销已加入代码，但尚未完成真实双设备联调。服务器仍可见关系、设备、时间、消息大小等元数据；控制事件（已读/删除）目前由已认证后端产生，尚无独立端侧签名。详情见[消息格式](../Protocol/Message_Format.md)。

## v4 在线文字与控制事件链路（两个独立模拟器已联调）

`V4Handshake` 用独立的 Curve25519 密钥协商与签名身份、签名预密钥、可选一次性预密钥，按带域分隔的握手记录派生共享密钥；发起前要求已核对的设备身份指纹。`V4RatchetState` 在内存中使用独立发送/接收链、DH 换钥、每消息密钥、消息头认证与有界乱序密钥缓存。局部测试覆盖双向消息、乱序、重放和篡改拒绝。

在线新建文字消息采用 v4 逐设备信封；旧 v1/v2 本地消息与 v3 网络消息仍按原版本读取。v4 私钥、预密钥私钥和 Ratchet 状态存于仅本设备可用的 Keychain，SwiftData 只保存版本与会话状态元数据。后端只存账号绑定的公开 v4 密钥、一次性公钥、密文信封和路由元数据。接收端核对已固定的 P-256 账号身份与签名绑定，再验证握手和 AES-GCM 认证标签，将正文用本地 v1 加密保存。

设备撤销后，服务端停止向它路由新消息、删除未用一次性公钥并使令牌失效；已签名的历史公开身份材料仅供核验撤销前已存储的信封。发送端的活动设备目录不会包含被撤销设备。

待发信封先加密写入本地队列，再推进 Keychain 中的发送链；接收端使用 Keychain 待提交记录协调本地消息、Ratchet 状态和同步游标，失败时停止确认。**这不是 SwiftData、Keychain 与后端的原子事务**；中断恢复依赖本机记录和幂等请求。v4 编辑、删除、已读和 Reaction 使用逐设备 Ratchet 认证密文；服务器仍可见事件类型和路由元数据。2026-09-27 在两个独立 iOS 模拟器与隔离的 HTTPS/Go/PostgreSQL/Redis 后端上，通过了首次建联、双向文字、已读、Reaction 添加/移除、编辑、删除以及一次离线待发恢复；大写 UUID 导致的已读事件 404 和重试阻塞已修复。实体设备、强制退出后的完整链路、故障注入、恶意服务器、公钥目录透明性和独立安全审计仍未完成。暂存的乱序消息密钥在消费前可恢复，Swift `Data`/CryptoKit 也不保证旧密钥从进程内存安全擦除。产品文案继续避免宣称“完整端到端加密”。

## v4 附件与人工身份核对（代码已接入，端到端联调未完成）

在线图片、文件和导入的语音文件现用独立随机 256 位附件密钥和 AES-GCM 加密。附件 ID、消息 ID、会话 ID、类型绑定为认证数据；文件名、密文哈希、对象 ID 和附件密钥只放入每设备独立的 v4 Ratchet 密文消息。本地附件密钥随描述信息由 Master Key 加密后存入 SwiftData；本地文件缓存也由 Master Key 加密。服务器只接收文件密文、大小、哈希、随机对象标识以及独立的消息密文。接收端按哈希及 AES-GCM 标签校验，下载失败可依据已保存的描述重试；删除本机消息或收到 v4 删除事件时清理本地密钥描述与缓存。服务端在 v4 删除事务内撤销附件下载权限，后台文件清理随后删除密文对象；已下载的对端副本不能强制擦除。离线时先保存加密待发意图，再在联网后上传密文并发送 v4 消息。已完成编译、三种类型的局部加解密/错钥/篡改测试，以及两个本机逻辑设备间的附件描述 Ratchet 传递；隔离 PostgreSQL 验证文件权限、消息绑定和删除墓碑。尚无两个独立设备经真实后端的附件闭环证据；上传成功但崩溃于记录对象 ID 前可能留下孤儿密文对象，需故障注入验证。

好友资料的“安全验证”从双方长期 P-256 账号身份公钥派生对称安全码，支持文字比较和二维码图片核对。首次固定或密钥变化后重新信任都要求用户经服务器外的渠道比较；客户端不能证明用户确实比较了另一人的设备。服务器可替换未核对的初始公钥、隐藏设备或拒绝服务；透明公钥目录与独立协议审计仍未完成。聊天顶部继续显示“隐私保护已开启”，不得启用完整 E2EE 标识。

## 2026-09-27 最终验证结论

本轮环境只有一台已登记但不可用的实体 iPhone，且没有运行中的联调后端；两台独立实体设备的注册、在线握手、双向文字、三类附件与事件闭环以及中断恢复均**未验证**。聚焦 iOS 模拟器测试通过附件 AES-GCM 错钥/篡改拒绝、安全码、Ratchet 重开和事件重放拒绝；隔离 PostgreSQL 中的后端处理器测试通过 v4 事件权限与幂等、设备撤销、公钥目录及文件权限。它们不能代替真机和完整在线链路。本轮还阻止在线历史被导出成无法恢复的便携备份，以免额外复制 v4 附件密钥描述。安全与隐私报告已校正到 v4 实际代码能力，聊天顶部保持非完整 E2EE 文案。当前**不满足**启用“🔒 端到端加密”标识的发布条件。

## Security Hardening 补充

发送与接收的 Keychain 待提交记录现显式标记 `prepared`、`applying`、`committed`、`failed`；旧记录缺少该字段时按 `prepared` 读取。发送侧仍须先持久化加密待发请求，再提交发送链；网络失败重试同一密文与幂等键。接收侧仅在本地数据和游标保存后重放提交 Ratchet 状态。该标记用于发现与重试中断事务，并不提供跨 Keychain、SwiftData、后端的原子提交保证。Debug 构建可查看版本、会话状态、事件 ID、游标和待处理数量；Release 不包含此入口或诊断服务。

附件随机密钥只在 v4 认证消息和本地主密钥加密的描述中保存。后端对超过 24 小时仍未关联消息的已验证密文上传作墓碑清理；客户端重试时需重新上传。附件删除清理本机描述与缓存，并由后端墓碑撤销下载权限；已下载副本及历史系统备份无法强制擦除。实体设备、故障注入和独立协议审查仍未完成，产品不得将此描述为已验收的完整 E2EE。

## Final Hardening：会话状态与 PreKey

v4 会话 Keychain 记录现在带单调 `stateVersion`。每次加密或解密推进后版本加一；保存时拒绝旧版本、同版本不同内容和跳号，并在独立的本设备 Keychain 记录中保存最高已提交版本。读取时若会话版本低于该记录，停止收发。旧会话和旧事务记录缺少版本时按 0 迁移，在下一次正常推进时写入版本 1。此检查能发现单条会话记录回退，不能抵御已解锁设备被完全控制或整个 Keychain 同时被回滚；Swift `Data` 也不提供可靠内存擦除。

本设备一次性 PreKey 的可领取库存由已认证设备专属接口查询；少于 20 个时补充到 100 个，待发布的公钥清单随私钥保存在 Keychain，上传失败可重试。同一公钥上传幂等。服务器领取时若任一目标设备库存耗尽，整个领取事务返回错误，不以缺失一次性 PreKey 的握手静默降级。此前已领走但尚未送达的密钥仍需保留以解密离线消息，因此本地 Keychain 池可能增长；公开目录仍可能被恶意服务器拒绝服务，不能视为密钥透明性证明。
